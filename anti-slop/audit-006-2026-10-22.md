# Full audit 006, 2026-10-22

Scope: production app at `scmining.vercel.app`, production Supabase data, current source, plan economics, casino controls, admin reporting, reset feature, payment flow, and security posture.

This file is the original audit snapshot. The remediation below was applied after the audit and is deployed.

## Remediation applied

- Plans repriced: Free 0.02 DOGE/day for 30 days, V1.1 0.24 DOGE/day for 90 days at $5, V1.2 2.37 DOGE/day for 90 days at $50.
- Pending $5 invoice canceled.
- Minimum withdrawal set to 10 DOGE; maximum 1000 DOGE.
- Casino max bet set to 10 DOGE; max win 1000 DOGE; extra edge set to 2%.
- Free plan is one-time only and no longer renews after expiry.
- Paid plans cannot be marked as the default starter plan.
- Plan saves are blocked when net margin is zero or negative, and when the live DOGE rate is unavailable.
- Owner reporting is in USD: cash collected, member balances, remaining plan liability, affiliate cost, processor fee, and owner position.
- Plan purchases are labeled as plan purchases, not cash deposits.
- Effective casino return and max win are shown on every game.
- Invoice pages show received or detected amounts, not the expected amount.
- Contact form moved to a throttled server route.
- Reset now clears contact messages, demo addons, and requires a backup acknowledgement.
- Referral ids use a database sequence.
- Admin home warns when an admin has no TOTP.

## Executive summary

Security is in good shape. The money model is not.

The current paid plans are deeply loss-making. The free plan is a five-year liability. The casino has no maximum win, so a single win can exceed the platform balance. The admin dashboards mix cash, site currency, and plan liability, so they can make the business look healthier than it is.

There are no paid invoices yet, so no loss has been realized. There is one pending $5 invoice. If it is paid, it creates a 1350 DOGE plan liability.

Do not market paid plans or the casino until findings 1 to 8 are fixed.

## Critical findings

### 1. Paid plans are insolvent

`lib/plan-math.ts` correctly shows the loss. The plan manager also warns about it. The values are still live and buyable.

At the current DOGE price:

- Plan V1.1 pays $110.76 for $5.
- Plan V1.2 pays $391.35 for $50.
- The pending $5 invoice would create a 1350 DOGE liability.

A 35% payout ratio is a safer model. It leaves about 62.75% after affiliate and processor fees at the current price. The break-even DOGE price is about $0.226 to $0.229, roughly 2.76x to 2.79x the current price.

Recommended starting values:

| Plan | Price | Daily | Days | Total DOGE | Value now | Gross margin |
|---|---:|---:|---:|---:|---:|---:|
| Free Plan | $0 | 0.02 | 30 | 0.6 | $0.05 | one-time starter |
| Plan V1.1 | $5 | 0.24 | 90 | 21.6 | $1.77 | 64.6% |
| Plan V1.2 | $50 | 2.37 | 90 | 213.3 | $17.50 | 65.0% |

These numbers are examples. The owner should approve the final values.

### 2. The pending $5 invoice is a live loss

Invoice `cf050c784850061a343bb23cf5bd7a5d` is pending. If it is paid, it activates plan V1.1.

At the current rate that is a $105.76 loss. Cancel it before testing or marketing.

### 3. The casino has no maximum win

Production settings:

- `games_max_win = 0`, which means no cap.
- `games_max_bet = 500 DOGE`.
- `limbo` allows a target of 1,000,000x.
- `plinko` high risk pays 1000x.
- `slots` top triple pays 1200x.
- `crash` caps at about 221.4x.

Theoretical maximum liabilities:

| Game | Max multiplier | Max bet | Max payout | USD at current price |
|---|---:|---:|---:|---:|
| Limbo | 1,000,000x | 500 DOGE | 500,000,000 DOGE | about $41,021,775 |
| Plinko | 1000x | 500 DOGE | 500,000 DOGE | about $41,022 |
| Slots | 1200x | 500 DOGE | 600,000 DOGE | about $49,226 |
| Crash | about 221.4x | 500 DOGE | 110,700 DOGE | about $9,082 |

The expected edge is positive, but one win can exceed the bankroll. Set a hard cap before more traffic.

Recommended starting values:

- `games_max_bet = 10 DOGE`
- `games_max_win = 1000 DOGE`
- `games_min_bet = 1 DOGE`

That caps the maximum effective win at 100x. Show the cap in the game UI and the bet confirmation.

### 4. Minimum withdrawal is zero

Production has `min_withdraw = 0` and `max_withdraw = 100`.

A free-plan user can request 0.02 DOGE. The network fee and manual review cost more than the payout. This is a direct loss and creates dust requests.

Recommended starting values:

- `min_withdraw = 10 DOGE` (about $0.82)
- `max_withdraw = 1000 DOGE` (about $82)

The free plan total of 0.6 DOGE cannot be withdrawn under this floor. Paid plans can.

### 5. A paid plan can be marked as the default free plan

`app/api/admin/plans/route.ts` accepts `is_default` on any plan. `lib/ensure-profile.ts` grants the default plan to a new user with no active rig.

If an admin marks a paid plan as default, every new account receives that paid plan for free. The plan manager label says "free starter rig" but the API does not enforce price 0.

Required guard:

- Reject `is_default = true` unless `price = 0`.
- Show the validation in the plan form.
- Keep exactly one default plan.

### 6. The free plan is a five-year liability and can renew

The free plan is 0.02 DOGE/day for 1825 days, about $2.99 per user. With 10,000 users that is about $29,900 in DOGE liability.

`lib/ensure-profile.ts` grants the default plan whenever the user has no active rig. After the free plan expires, the next dashboard visit can grant another one.

Recommended:

- Shorten the free plan to 30 days.
- Make it one-time per user.
- Grant only when the user has no plan history at all, not merely no active rig.
- Keep the total small, for example 0.6 DOGE.

### 7. Plan purchases are recorded and displayed as deposits

`activate_paid_invoice` inserts a `user_deposits` row with the site DOGE amount. It does not credit the member balance. The plan yield is separate.

The UI then calls this a deposit:

- `app/account/page.tsx` shows it under Deposits.
- `app/dashboard/page.tsx` labels it "Deposit received".
- `lib/catalog.ts` includes it in the public payout feed.
- `app/admin/page.tsx` sums it as "Deposits in".

A $5 plan shows a 60.4 DOGE deposit in history, but the member balance is still zero. The owner dashboard then treats 60.4 DOGE as cash in, when the actual cash was $5.

This is both a comprehension problem and an accounting problem. Separate plan purchases from cash deposits, or label the record as a plan purchase and store the actual paid amount and coin.

### 8. Owner reporting uses the wrong units and labels

`app/admin/page.tsx`:

- `depositsIn` sums `user_deposits.amount`, which is site DOGE credited by plan activation, not cash collected.
- `netFlow` is deposits minus paid out, in DOGE.
- It is labeled "Gross margin" and "Surplus/Deficit".
- It does not subtract plan payout liability, affiliate cost, or processor fees.
- `avgMargin` is always colored emerald even when negative.
- `activeRigs` counts status active without checking `expire_date`.

`app/admin/analytics/page.tsx` uses `price_amount` for revenue, which is closer to cash, but it does not show payout liability or owner margin. It also falls back to `amount` when `price_amount` is null, which mixes DOGE and USD.

Use one unit and one definition:

- Cash collected: paid invoice `price_amount` in USD.
- Accrued liability: member balances in DOGE converted to USD.
- Paid out: successful withdrawals in DOGE converted to USD.
- Remaining plan liability: remaining daily credit times remaining days for active rigs.
- Owner margin: cash collected minus affiliate, processor fees, paid out, and remaining liability.

### 9. The free plan and plan liability are excluded from the plan profit summary

`components/admin/plans-manager.tsx` sums owner profit across paid plans but sets the default plan to zero. It also labels the sum "per paid sale".

The owner cannot see the free-plan liability, and the sum is not a per-sale number when more than one plan exists.

Show:

- Free-plan cost per user.
- Profit per sale for each paid plan.
- Total profit if one of each plan sells.
- Liability already sold but not yet paid.

### 10. The plan calculator can show a false 100% margin

`app/admin/plans/page.tsx` sets `cryptoToPrice = 0` when the FX table is unavailable. `planEconomics` treats 0 as no conversion cost, so owner profit becomes the full price and margin becomes 100%.

A temporary rate failure can make a loss-making plan look profitable.

Fail closed: show "rate unavailable" and block the save, or use the last known rate with a timestamp.

### 11. The app claims mining and hashrate but sells fixed daily credits

The public UI says:

- "Mine Dogecoin from a console, not a warehouse."
- "Hashrate plans."
- "Live hashrate", with a DOGE per minute value.
- "Your rigs are mining X per day."
- "Hashrate" fields that are labels like 1, 10, 100.

The product actually credits a fixed daily DOGE rate. There is no verifiable hash output, pool share, or miner identifier.

If the business operates real miners, show proof and explain how fixed credits relate to actual output. If it does not, rename the product to a rewards or yield plan and remove the mining claims. This is the largest trust risk after the losses.

## High findings

### 12. Effective casino return is hidden

Production has `games_edge_boost = 3`. The game header shows the base edge, for example "Base 1% house edge". It does not show the extra 3%.

Approximate effective RTP:

| Game | Base RTP | Effective with +3% |
|---|---:|---:|
| Dice, Limbo, Crash, Coinflip, Wheel, Mines | 99% | 96% |
| Plinko | 97% to 99% | 94% to 96% |
| Roulette | 97.3% | 94.3% |
| Slots | 92% | 89% |
| Keno | about 90% | about 87% |

The UI should show effective RTP or "total house edge" per game. The current copy can make users expect 99% and receive 96% or less.

Recommended: global extra edge 2%, and no extra edge on slots and keno, or show the exact effective number for every game.

### 13. Maximum win is not shown in the game UI

The game page passes only `minBet` and `maxBet` to `GameView`, `CrashView`, and `MinesView`. It does not pass `maxWin` or the effective edge.

The server caps payouts in `applyPayout`, but the client cannot show the cap before the bet. A user can see a 1000x prize and receive a capped payout.

Pass `maxWin` and effective RTP to the game views, show them beside the bet, and show the capped payout in the result.

### 14. Overpayments and underpayments are not fully explained

`app/api/webhooks/cryptapi/route.ts` accepts any amount at or above the invoice amount, then credits the fixed plan amount. The extra crypto stays with the owner.

The invoice says underpayments are not credited. It does not say overpayments are not refunded or credited.

Add a plain policy:

- Send the exact amount.
- Underpayments may be lost and are not credited.
- Overpayments are not refunded unless support approves it.
- Wrong coin or wrong network may be lost.

If the owner wants to be fair, refund or credit overpayments manually and say so.

### 15. Invoice labels show the expected amount as if it were actual

`app/invoice/[hash]/page.tsx` shows "Amount paid" when the invoice is paid and "Amount sent" when it is waiting. Both display `params.amount`, which is the expected amount, not the actual amount received.

If a partial payment triggers a waiting state, the page shows the full expected amount as sent. If an overpayment is confirmed, the page shows the expected amount as paid.

Store and display the actual received amount and coin from the webhook.

### 16. Plan prices change with the display toggle

Plan cards use `formatPrice`, which shows a DOGE equivalent when the visitor selects crypto display. The purchase page shows the price in USD plus a local fiat hint.

The same plan can show a DOGE price on one screen and a USD price on the next. Users cannot tell which number is the actual price.

Show the USD price as the price, and show the local fiat or DOGE equivalent only as a secondary "approximately" line.

### 17. The reset does not clear contact messages and has no backup step

`supabase/025_reset_progress.sql` clears members and most activity but leaves `public.contact` untouched. Contact messages are member activity and should be part of the reset.

The reset is irreversible and there is no backup prompt. Supabase PITR is not enabled. Add a "download a backup first" step, or require a recent backup before the reset button is enabled.

### 18. One of two admin accounts has no TOTP

Production has two admins, one with 2FA and one without. The admin APIs require TOTP and a fresh code, so the unprotected admin cannot use admin tools.

Enroll the second admin before relying on the account, or remove admin access from it.

### 19. The public "Deposits" feed shows plan purchases, not cash deposits

`lib/catalog.ts` includes `user_deposits` in the public payout feed. Those rows are created by plan activation, not by a separate cash deposit.

A visitor can see a 60.4 DOGE "deposit" that was actually a $5 plan purchase. The amount is the site currency equivalent, not the coin the buyer sent.

Rename the feed entry to "Plan purchase" or show the actual paid coin and amount.

### 20. The payout page opens on a canceled request

The only withdrawal in production is a canceled 100 DOGE request. The payout page defaults to "All", so a new visitor sees a canceled request and no completed payouts.

The copy now explains canceled is not paid. That helps. For trust, default the page to completed payouts, or show canceled only under the Withdrawals filter.

## Medium findings

21. `app/admin/page.tsx` counts admins in "Total members". `app/admin/analytics/page.tsx` excludes them. Use one definition.

22. `app/admin/page.tsx` counts active rigs without checking `expire_date`. The public stats do check it. Expired rigs can inflate the admin number.

23. `app/admin/analytics/page.tsx` uses `price_amount ?? amount`. If an old invoice has no `price_amount`, a DOGE amount is counted as USD. Use the paid invoice price only, or flag missing prices.

24. `app/admin/plans/page.tsx` displays "Hashrate" for an arbitrary label. Use "Relative speed" or "Plan tier" unless the value is a real hash rate.

25. The plan form accepts a negative-margin plan with only a warning. For a profitable product, block save below a minimum margin, or require an explicit "loss-making promo" confirmation.

26. The plan form does not include affiliate cost, processor fee, or DOGE volatility in the owner calculator. Add them, plus a +50% and +100% DOGE sensitivity row.

27. The free-plan total is shown as "Projected over 1825 days". It is mathematically correct but looks like a five-year promise. Use a 30-day starter and show the short term.

28. `app/purchase/[planId]/page.tsx` creates a CryptAPI address before checking the network minimum. A direct API call can create an orphan address. Check the minimum first.

29. The 20-minute invoice window is not enforced for credit. A late payment still credits. The invoice page says this, but the status should make it explicit after expiry.

30. The contact form inserts into a table with `INSERT` allowed for `public` and no rate limit or CAPTCHA. It can be spammed. Add a throttle or bot check.

## Low findings

31. Development dependencies still show 9 advisories, 7 high, from Tailwind 3, `braces`, and `postcss-selector-parser`. Production audit is clean. The fix requires Tailwind 4, which is a breaking change.

32. `ensureProfile` generates `unique_id` with `Math.random()` and only six retries. Collisions are unlikely now but not guaranteed at scale. Use a database sequence.

33. `ensureProfile` silently swallows errors. If profile creation fails, the dashboard can render without a profile. Surface the failure in admin diagnostics.

34. The reset preview does not show contact messages. Add them to the preview and the SQL.

35. The reset does not remove `addons` or `addon_demo`, which are legacy demo rows. They are not member data, but a full fresh start should remove or ignore them explicitly.
